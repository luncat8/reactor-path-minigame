# 0.1 — Reactor path experiment

## Goal
Tune a single particle, representing a beam, into a stable trajectory that activates several targets evenly without crossing cooling zones. The path is a continuously revised, finite prediction, not a prescribed closed curve. Guidance attracts the particle toward nearby path segments and aligns its velocity without teleportation.

## 0.1.1 Runtime and architecture
- Open `index.html` directly: classic scripts, local assets, no dependencies or build.
- Separate deterministic simulation (`js/reactor.js`) from canvas rendering and input (`js/app.js`). Export the simulation conditionally for Node tests.
- Use a fixed simulation timestep, bounded catch-up, reusable forecast buffers, and a logical arena independent of viewport size.
- Provide pause, single-step, reset, and forecast/guidance controls for investigation.

## 0.1.2 Particle dynamics and guidance
- Begin with a weak anisotropic restoring field producing orbit-like motion. This is a gameplay model, not a physical reactor or Lorentz-force simulation.
- Add softened, bounded magnet forces. Magnets move along the perimeter; orientation changes their field; polarity switches attraction/repulsion.
- Sample a finite forecast into position and timestamp buffers. Periodically predict again from the live particle, using the previous forecast as a weak guide with diminishing influence beyond its time horizon.
- Guide the beam against a **committed route**: the trajectory it announced, held as the reference for a configurable route memory (default 1.8 s, 0 disables) instead of being replaced by every new prediction. A prediction started from the live beam is already the beam's ballistic continuation, so a reference that tracks the newest prediction makes zero force a fixed point and leaves guidance nothing to correct. Holding the route restores real error terms whenever the beam or the field changes, while the trajectory still evolves smoothly instead of jumping after an edit.
- Locate the guide point as the **true nearest point** of the committed route: project the beam onto its segments, interpolate, and never snap to a stored sample. The projection window walks the route from the anchor's own arc length by the beam's plausible advance, so the anchor follows the route the beam is flying — a self-crossing pass cannot capture it, and a plan whose timestamps run ahead of the beam cannot be projected behind it. Restrict candidates to segments that continue the beam's heading, and report guidance idle rather than guessing a correction.
- Aim one forward-aim interval (default 100 ms of route arc) beyond the projection and apply only the component of that correction lateral to the beam's velocity: the force is perpendicular to the velocity by construction, so guidance can steer but never thrust, brake or point backwards, and an on-route beam needs no correction at all. Fade the force with cross-track distance and with the heading error against the route direction at the projection; ignore opposing and perpendicular passes, and never snap position or velocity onto the guide.
- Refresh the anchor after each integration step, because the integration steers from the position at the start of the step: a ring drawn from the pre-step projection trails the beam by one step and reads as a backwards pull. The published ring, aim, force and readout then all describe the state on screen, and the published force is the one the next step applies.
- Use the same integrator and collision rules for live and predicted motion. Reuse buffers; forecast work is periodic rather than every render.
- Tune horizon, guide strength, forecast cadence, and force limits using deterministic experiments. Stable-but-adjustable behavior matters more than physical fidelity.

## 0.1.3 Reflectors and controls
- Provide short, rotatable segments in the chamber. Reflect only when the incoming direction forms a shallow angle with the surface; steep impacts pass through.
- Detect swept crossings to avoid tunneling and move through the remaining timestep after reflection.
- Select a magnet or reflector on canvas; drag magnets along the frame. Rotate the selection using a slider or wheel. Provide keyboard selection/movement/rotation alternatives and visible selection feedback.

## 0.1.4 Activation and cooling
- Targets and cooling zones are transparent to particle motion.
- Compute segment-circle overlap and multiply by timestamp differences to integrate dwell time, rather than counting samples or entries.
- Forecast target duty cycles and cooling exposure over the finite horizon. Display signed percent deviation from each target's requested duty cycle next to it.
- Track actual target activation with a time-smoothed dwell signal. Keep actual and predicted signals distinct.
- Define stability from target balance and cooling avoidance. Require sustained acceptable live activation for a stable status; do not treat forecast balance as a completed objective.

## 0.1.5 Presentation and validation
- Dark instrument-panel presentation with clear trajectory, beam, zones, controls, target bars, and a compact legend. Responsive layout and high-DPI canvas.
- Debug overlay: committed route, amber forecast forces, cross-track line, the green ring on the route's true nearest point (the target the lateral pull works toward, and the point the arrow therefore points at), the amber dot on the look-ahead point, the white live steering arrow and a numeric readout of route age, off-route distance, heading error and the exact force. Draw the arrow only above a threshold where the pull is more than tracking dust, and scale arrow lengths compressively (square root), since a minimum length makes noise-level forces look like full-strength pulls.
- Automated Node checks: determinism, finite bounded motion, magnet influence, true-nearest projection and its independence from plan timestamps, exactly-lateral steering, the force pointing from the beam at the nearest route point, anchor continuity across crossing passes, route memory commits, forecast timestamps, dwell geometry, and grazing versus steep reflections.
- Browser checks: direct-file loading, rendering, pointer and keyboard controls, pause/reset, resizing, and no runtime errors.

## 0.1.6 Follow-up tuning
- Measure how quickly forecasts converge and how far they diverge after magnet edits.
- Sweep guide strength, route memory and forward aim against target duties and cooling exposure; the route memory in particular decides whether the guide reads as "stable but adjustable" or as a rail.
- Establish solvable scenarios and calibrated target duties using scripted parameter sweeps and playtesting.
- Add presets, difficulty levels, and persistence only after the underlying tuning loop is useful.
- Consider spatial indexing or chunked forecast computation if profiling shows periodic stalls. Avoid introducing workers or dependencies without evidence.
