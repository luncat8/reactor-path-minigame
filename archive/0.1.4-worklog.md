# 0.1.4 worklog — 2026-10-05

## Prompt (draft)
Guidance problems reported after the cross-track commit: the debug overlay "failed to detect the
proper nearest trajectory point and showed just the next position on the same line", and the force
direction was "sometimes backwards" which should be impossible given the 90° direction gate plus a
look-ahead. Request: fix the nearest-point detection and the debug display, and refactor the whole
guide force if that is what it takes.

## Diagnosis (measured, not guessed)
- Nearest point: `nearestNode` scanned every forecast node and returned a *sample*, so the ring was
  drawn up to half a sample away from the true closest point on the polyline. Worse, when no node
  passed the direction gate it fell back to the globally closest node, which can be an opposing pass.
- Backward force: measured over 60 s at the default settings, **50 %** of the guide-force samples
  pointed backwards relative to the velocity (up to 180°). The coast-corrected aim `aim − (p + v·h)`
  is a *speed* correction: whenever the beam is ahead of schedule the correction points backwards.
- Inert guide: the same run showed the guide at a median 0.148 acceleration against a median field
  of 124.7 — **0.12 %** of the field. The beam sat within 2 px of the plan it was *scheduled* to be
  at in the same instant, because the plan is generated from the beam's own state with the same
  dynamics. A reference derived from the live state therefore makes zero force a fixed point:
  guidance only ever saw the beam sitting on its own ballistic continuation.
- Debug honesty: the live arrow was drawn with `max(20, magnitude·8)` px, so a 0.05 noise force got a
  20 px arrow while a 5.0 force got 40 px. Most of what the overlay showed was noise scaled up.

## Development
- `js/reactor.js`
  - Forecast plans now carry cumulative arc length `s`; a **committed route** (`reference`) is held
    from the plan adopted at the last commit and re-committed once the selected **route memory**
    expires (default 1.8 s, quantised to the 0.6 s refresh, 0 disables). Both the live beam and the
    forecast are generated against that route, so guidance finally has error terms to correct while
    the trajectory still evolves smoothly. Commits also happen immediately when the clock stands
    still (field edits while paused) so the display stays responsive.
  - `findGuidePoint` replaces `nearestNode`: it projects the beam onto the reference *segment*,
    seeded on the sample the route scheduled for the current instant, walking a bounded arc-length
    window and accepting only segments that continue the beam's heading. It reports the true
    projected point, the local route speed and the cross-track distance, and returns false (guidance
    off) instead of guessing when nothing forward-aligned exists.
  - `guidanceVector` aims one look-ahead interval of arc length ahead of the projection and applies
    only the part of the correction **lateral to the beam's velocity**. Guidance can no longer
    thrust or brake by construction, so "never backwards" no longer depends on a gate passing.
  - Removed `nearestNode`, `GUIDANCE_DELAY`/`GUIDANCE_FADE` and `guidanceRamp`: the route memory
    replaces the forecast dead zone. Debug sink now carries the interpolated nearest/aim points, the
    cross-track distance, the heading error, the force magnitude and the route age.
- `js/app.js` / `index.html` / `style.css`
  - Debug overlay: dashed amber cross-track line from the beam to its projection, ring on the
    projected route point, dot on the look-ahead point, white steering arrow, plus the committed
    route drawn as a dashed violet line. Arrow lengths now use a square-root scale so a small force
    reads as small, and a monospace readout prints `route age · off-route px · heading° · force`.
  - New **Route memory** slider; guidance micro-copy rewritten for the committed-route model.
- `tests/reactor.test.js`: projection instead of node snapping, structural never-backwards check over
  a grid of offsets and headings, opposing/perpendicular passes, falloffs, route-memory commit
  interval, held-route deviation and field-change engagement, long bounded runs with memory on/off.
- `experiments/guidance-probe.js`: deterministic measurement of geometry, telemetry, memory sweep and
  paired before/after response to a magnet flip.

- `node --test tests/*.test.js`: 17 passed. `experiments/guidance-probe.js` at the defaults reports

## Limitations and next step
- The guide is a bounded steering term (max 50 within a ~125 field), so it can hold a route that the
  field roughly supports but cannot force a route the field does not: after a large magnet edit the
  beam adopts the new orbit and the guide yields through its distance fade.
- On-route forces are deliberately small, so the debug arrows are near zero during quiet tracking;
  the readout is the honest indicator there. The absolute authority is still tuned by eye, not swept.
- Duties and cooling remain uncalibrated; no winning preset exists, and the default scenario still
  misses target B.

**Suggested next step:** sweep guide strength, route memory and look-ahead against target duties and
cooling exposure to calibrate one solvable scenario, then playtest whether the committed route reads
as "stable but adjustable" rather than as a rail.
