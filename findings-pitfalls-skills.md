# Findings and pitfalls

- Keep forecast and live simulation buffers separate. Forecasting must copy the particle into reusable scratch state and must not accumulate live activation or advance the live clock.
- At trajectory crossings, nearest position alone can choose an opposing segment. Prefer segments that continue the heading, and limit guidance acceleration instead of snapping velocity.
- Aiming a guidance vector straight at a look-ahead node pushes an on-track beam forward (thrust, not steering), so every debug vector points along the path. Measuring the correction relative to where the beam would coast fixes thrust but adds a *speed* term that points backwards whenever the beam runs ahead of schedule. Keep only the component lateral to the beam's velocity: steering stays possible, thrust and braking become impossible by construction, and no gate has to be trusted.
- A reference trajectory derived from the live state is already that state's ballistic continuation, so "no force" is an exact fixed point of the whole guidance loop and the guide can never do visible work. Hold a committed reference (a plan from before the current perturbation) and the error terms are real again.
- Track a self-crossing forecast by projection onto segments, never by scanning for the nearest node: node scans snap to samples and can return an opposing pass. But do not seed that projection on "the sample the plan scheduled for the current instant" either — a plan whose timestamps run ahead of the beam (a beam flying faster than the schedule it announced) then puts the search window hundreds of pixels away and the reported nearest point is nowhere near the beam. Seed the window on the anchor's own arc length, sized by the beam's plausible advance, and use timestamps only as a hint that the plan is stale, never as the location of the nearest point.
- A guided beam flies its own plan: the projection is taken from the position at the start of the integration step, so any debug geometry published from that snapshot trails the beam by one step (1.2 px at 145 px/s) and reads as a target behind the beam, roughly 180° from the velocity, even when the projection is mathematically exact. Re-project after the step and publish that, or publish the force as "the one the next step applies" — then ring, dot, arrow and readout all describe the same instant.
- Draw the ring at the point the force actually works toward. With a lateral force (the component of the aim correction perpendicular to the velocity), `perp_v(aim − p) = perp_v(P − p) + L·perp_v(T)`: the first term points exactly at the route's nearest point `P` for a parallel beam and dominates whenever the cross-track error is real, while the look-ahead `L` only adds heading alignment. Measure the drawn geometry against the physics (ring-to-beam gap, force-to-ring angle), not by eye: here the arrow sat 2.2° off the ring on average and the rare corner-overshoot frames where the heading term dominates are explained by the heading-error readout.
- Verify overlay thresholds against measured distributions before choosing them. A live steering arrow drawn from ~0.04 upwards turns sub-0.2 tracking dust into constant decoration; at 0.25 it appears in ~13 % of frames during heavy magnet dragging, which is when a correction is real. Always pair a display threshold with a numeric readout of the exact value so the overlay never claims the force is zero.
- Debug arrows must be scaled honestly. A `max(minimum, magnitude·k)` length gives a 0.05 noise force the same 20 px arrow as a real pull, which reads as "the force is wrong" instead of "the force is idle". Use a compressive scale (square root) plus a numeric readout of the actual value.
- Target influence is dwell time, not entry count. Segment-circle overlap multiplied by timestamp differences makes forecasting less sensitive to sample spacing.
- Preserve classic script loading and guarded CommonJS exports so the same core runs under `file://` and Node tests without a build.
- Keep browser tooling external to the runtime tree. The optional Playwright experiment accepts `BROWSER_EXECUTABLE` for environments where automatic browser downloads are unavailable.
